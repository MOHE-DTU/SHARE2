Portal vs Aplikasi

Penerangan teknikal, perbezaan kos & contoh sebenar dalam ekosistem KPT
🌐
Portal
Gerbang Bersepadu
Definisi
Pintu masuk tunggal yang menggabungkan pelbagai perkhidmatan atau aplikasi dalam satu antaramuka. Pengguna log masuk sekali (SSO) dan boleh akses semua fungsi.
Analogi
Seperti KLCC — satu bangunan besar, banyak kedai di dalamnya. Pengunjung masuk sekali melalui satu pintu, boleh ke mana-mana bahagian.
Pengguna sasaran
Pelbagai jenis pengguna (awam, staf, pentadbir) dalam satu platform merentasi domain berbeza.
Contoh dalam KPT
Portal KPT myGOV Malaysia Portal UPU Portal GREaT
⚙️
Aplikasi
Sistem Spesifik
Definisi
Sistem yang direka untuk satu tujuan atau domain yang spesifik. Ia menguruskan proses perniagaan tertentu dengan logik, data, dan aliran kerja tersendiri.
Analogi
Seperti kedai dalam KLCC — masing-masing ada operasi, stok, dan pekerja sendiri. Boleh wujud secara bebas atau sebagai sebahagian daripada portal.
Pengguna sasaran
Pengguna dalam domain tertentu sahaja. Contoh: aplikasi biasiswa — hanya untuk pemohon dan pegawai biasiswa.
Contoh dalam KPT
MyMoheS HRMIS MyBrain UPUOnline iGFMAS
Perbezaan Utama
Portal — mengintegrasikan banyak fungsi, satu log masuk, satu URL utama
Lebih kompleks dari segi seni bina — perlu SSO, hak akses, API routing
Kos pembangunan dan penyelenggaraan lebih tinggi
Aplikasi — satu fungsi/domain, boleh ada log masuk tersendiri
Lebih mudah dan cepat dibangunkan — skop terhad, lebih mudah diurus
Kos lebih rendah tetapi berisiko silo jika tidak diselaraskan
🌐
Portal — lapisan teknikal
UI Layer
Frontend (React/Vue) + Design System
Auth Layer
SSO / OAuth2 / MyDigitalID / Keycloak
API Gateway
Routing, rate-limit, load balancer
Microservices
Pelbagai servis bebas (App A, B, C...)
Data Layer
Data lake, shared DB, caching (Redis)
Infrastruktur
Cloud / Awan Kerajaan + CDN + monitoring
Memerlukan 6 lapisan penuh — setiap lapisan perlukan kepakaran tersendiri, pasukan lebih besar, dan kos yang lebih tinggi.
⚙️
Aplikasi — lapisan teknikal
UI Layer
Frontend (modul spesifik sahaja)
Auth Layer
Log masuk sendiri atau ikut portal
API
REST/SOAP endpoint (domain sendiri)
Business Logic
Peraturan perniagaan spesifik domain
Database
DB sendiri (MySQL / PostgreSQL / Oracle)
Infrastruktur
Server sendiri atau dikongsi
Lebih ringkas — skop terhad membolehkan pasukan kecil (2–5 orang) mengurusnya dengan efektif.
⚠ Perbezaan Kritikal dari Segi Teknikal
Portal memerlukan komponen tambahan yang tidak diperlukan oleh aplikasi biasa: API Gateway untuk menguruskan routing antara servis, Identity Provider untuk SSO merentasi semua aplikasi, Session management yang kompleks, dan Orchestration layer untuk memastikan semua komponen berfungsi selaras. Setiap lapisan tambahan ini menambah kompleksiti, kos, dan keperluan kepakaran teknikal yang lebih tinggi. Inilah sebab portal biasanya memerlukan pasukan IT yang besar dan masa pembangunan yang panjang.

Implikasi bagi KPT — perspektif WoG:
Jika 10 bahagian masing-masing bangunkan aplikasi sendiri tanpa penyelarasan, kos gabungan boleh mencecah RM 5jt – 20jt hanya untuk pembangunan. Dengan pendekatan WoG — berkongsi satu platform atau API bersepadu — kos boleh dikurangkan sehingga 40%–60%, di samping mengurangkan kos penyelenggaraan dan keperluan pasukan IT yang besar di setiap bahagian.
Portal myGOV Malaysia
Apa yang dilakukan: Satu pintu masuk untuk semua perkhidmatan kerajaan — dari renew lesen hingga semak cukai. Pengguna log masuk sekali dengan MyDigitalID.

Kerumitan: Menggabungkan lebih 44 perkhidmatan dari 16 agensi berbeza. Memerlukan SSO, API Gateway, dan sistem hak akses yang kompleks merentasi agensi.

Kos lebih tinggi kerana: Perlu memastikan semua agensi ikut piawaian sama, menguruskan versi API, uptime 99.9%, dan menyokong jutaan pengguna serentak.
Portal Portal UPU (upu.mohe.gov.my)
Apa yang dilakukan: Pintu masuk untuk semua urusan kemasukan universiti awam — permohonan, semakan status, rayuan, dan panduan kelayakan.

Kerumitan: Memuatkan UPUOnline, e-Panduan, UPUSelect dan UPUPocket dalam satu ekosistem. Perlu menguruskan lonjakan trafik semasa musim permohonan (ratusan ribu akses serentak).

Kos lebih tinggi kerana: Infrastruktur mesti mampu tanggung beban tinggi dengan sistem backup dan disaster recovery yang kukuh.
Aplikasi MyBrain15 (sistem biasiswa pasca siswazah)
Apa yang dilakukan: Mengurus permohonan, kelulusan, pembayaran elaun, dan pemantauan kemajuan pelajar biasiswa MyBrain15 sahaja.

Kerumitan: Skop terhad kepada satu program biasiswa. Logik perniagaan spesifik — syarat kelayakan, kadar elaun, keperluan laporan kemajuan.

Kos lebih rendah kerana: Domain terhad, pengguna sedikit (pemohon biasiswa + pegawai KPT), tidak perlu tanggung trafik tinggi atau kompleksiti SSO merentasi agensi.
Aplikasi MyMoheS (data pelajar IPTA)
Apa yang dilakukan: Pangkalan data berpusat untuk maklumat pelajar semua IPTA — enrolmen, program, dan prestasi akademik.

Kerumitan: Walaupun skop adalah "satu aplikasi", ia menguruskan data berskala besar dari 20 IPTA. Integrasi dengan sistem dalaman IPTA masing-masing menambah kerumitan.

Nota WoG: Ini contoh aplikasi yang berpotensi menjadi tulang belakang platform bersepadu — jika sistem lain merujuk data daripada MyMoheS, kita elak duplikasi data pelajar merentasi bahagian.

Cadangan DTU untuk RPTM 2026–2035:
Daripada 29 inisiatif digital yang dikenal pasti, kebanyakannya adalah aplikasi — lebih cepat dan murah dibangunkan. Pendekatan WoG yang dicadangkan adalah untuk memastikan aplikasi-aplikasi ini berkongsi infrastruktur, data, dan identiti pengguna yang sama, mengelakkan pembinaan silo, dan pada masa yang sama menyediakan landasan untuk diintegrasikan ke dalam portal myGOV apabila telah matang. Ini menjimatkan kos 40%–60% berbanding setiap bahagian membangunkan sistem secara berasingan.
